# 设计说明

## 目标与约束

Agent 的能力数量会增长，全塞进 system prompt 不可持续。要求：平时只暴露「名字 + 一句话描述」，
需要时才加载正文，正文提到的附带文件再按需读取；同时保证坏技能不影响启动、同名有确定规则、
技能多了注入长度可控、改文件后下一轮即生效。

## 模块与数据流

```
skills/{builtin,team,personal}/<name>/SKILL.md
        │  frontmatter.parse
        ▼
SkillRegistry.snapshot()  ── 指纹 (path,mtime,size) 变化才重扫 ──►  Snapshot
        │                                                          │
        │                        ┌─────────────────────────────────┤
        ▼                        ▼                                 ▼
inject.build_skill_section  tools.load_skill / read_skill_file   router.route
   (system prompt 技能段)         (正文, 附带文件, 依赖闭包)         (offline 选技能)
        └────────────────────────────► agent.run_turn ◄────────────┘
                                          │
                                     turn trace（步骤、加载、文件、token、费用）
```

`Snapshot` 是只读快照，任何一轮对话都基于同一份快照，避免扫描途中文件变化导致前后不一致。

## 决策

**frontmatter 解析器自己写，不引 PyYAML。** 目的是「一条命令启动」不依赖网络安装，而且要能给出
人类可读的错误定位（行号 + 具体原因）。支持的子集：顶层标量、单层 mapping、`- item` 列表、
`[a, b]` 行内列表、注释剥离、CRLF。超出子集即报错，而不是猜测——猜错描述会静默污染路由。

**坏技能隔离。** 解析失败收集 `reasons` 放进 `skipped`，扫描继续。同时列出「冗余」的失败：
例如坏技能同时有 tab 缩进、缺 description 时，两条原因都给出来，评审不必反复试错。

**同名冲突规则：来源优先级高者胜，落败者标记但不删除。** `personal > team > builtin` 是常见的
覆盖直觉（个人覆盖团队覆盖内置）。落败者保留在 `shadowed` 里，UI 显示 `override builtin`，
好处是评审一眼能看到「覆盖发生了」，而不是疑惑为什么少了一个技能。规则写进 UI 文案，避免猜。

**注入分级而不是硬截断。** 直接按字符截断会让所有描述都残缺；直接丢技能会丢掉用户真正要的
能力。四级策略（full → compact → tight → truncated）先牺牲描述精度（名字还在，模型仍能按名
加载），最后才按优先级丢列表项，并在末尾声明「还有 N 个未列出」。这样模型仍有机会通过
`load_skill` 使用未列出的技能（运维侧可提供名字），而 prompt 长度有硬上限。

**token 估算。** CJK 1 字符 ≈ 1 token、其余 4 字符 ≈ 1 token。比真实分词器略保守，宁可少列几个
技能，也不超预算。代价：同一份 prompt 真实 token 会比显示值小 5-15%。

**热更新用指纹而不是文件监听。** 监听器在 Windows/容器里行为不一致，且需要常驻线程；指纹比对
发生在每次取快照时，实现简单、行为可预测，代价是每次请求做一次轻量 stat 遍历（12 个技能约 1ms）。

**路径穿越防护分两层。** 先做字面拒绝（绝对路径、盘符、`..`、NUL），再 `resolve()` 后校验
「解析结果必须仍在技能目录内」。第二层才挡得住符号链接指向外部的情况。测试里两种都覆盖。

**依赖解析 DFS + 三色标记。** `visiting/done` 两态即可检测环，环时报出完整路径
（`cycle-a -> cycle-b -> cycle-a`）便于定位。依赖先于依赖者返回，正文按 `order` 一次性给模型，
避免模型多次往返。

**脚本沙箱是 Python 级限制。** 临时目录副本 + 超时 + 清空环境变量 + `sitecustomize` 禁用 socket
+ 输出截断。它挡住的是「脚本顺手联网」「脚本死循环」这两类常见事故，不防恶意本地文件写入——
真正的隔离需要容器或作业对象。选它是因为零依赖、跨平台、行为可预期；README 与这里都写明了
边界，不假装是 OS 沙箱。

**离线模式是显式降级，不是模拟。** 没有 API key 时对话与评测都用确定性 BM25 路由器，trace 里
`mode=offline`，`llm_calls.jsonl` 记 `ok=false` 与原因。这样演示可跑、评测可复现，同时不会把
「没调用模型」伪装成调用过。

## 评测设计

评测集 20 条：17 条对应某个具体技能（含口语化与易混表达），3 条为负例，应当不使用任何技能。
每条标注 `expected`（或 `null`）与 `category`。

两个描述版本保存在 `eval/description_variants.json`，评测时作为 `descriptions` 覆盖传入
路由器，所以即便 SKILL.md 已经被改成 tuned 版本，baseline 数字仍可复现。

指标：准确率（含负例）+ 错误用例 id + 每条 top-5 分数。对比输出 `fixedCases` / `regressedCases`，
避免只看总准确率掩盖回归。

结果：baseline 90.0%（c01、c02 被两条相似描述互相吸走），tuned 100.0%，回退 0。可复现命令
`make eval`。

## 页面

左：技能列表（来源、是否被覆盖、行 token、正文 token、本轮是否被加载）、跳过原因、同名冲突、
选中技能的正文/附带文件预览。右：对话，每轮展示步骤（inject / route / tool_call / tool_error）、
加载的技能、读取的文件、prompt token 与级别、本轮指纹。下：评测表格与大模型费用。
顶部调试面板：重新扫描、模拟 200 个技能、预算输入。样式朴素是刻意的（题目要求样式不重要）。

## 取舍与下一步

- 想减少误判，可以把离线路由器换成本地小模型 embedding，但会引入依赖与启动成本；当前选择
  可复现优先。
- 预算策略目前按「优先级」丢弃，若技能带使用频率统计，应按「期望收益」丢弃。
- 脚本沙箱如果要真正隔离，下一步是把 `sandbox.py` 的执行入口挪进容器，接口保持不变。
